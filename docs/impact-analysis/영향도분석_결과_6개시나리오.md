# DDL·샘플 코드 기반 영향도 분석 결과

분석일: 2026-11-06

분석 대상: `samples/obix-source` 및 `samples/obix-source/database-DDL.txt`

## 1. 분석 범위와 결과 요약

요청한 세 유형에 대해 실제 코드에 존재하는 대상을 선정하고 유형별 2개, 총 6개 변경 시나리오를 작성했다. 각 시나리오는 3턴의 질문과 예상 답변으로 구성했다. **변경은 가정이며 실제 ALTER·삭제·코드 수정은 수행하지 않았다.**

| 유형 | 변경 가정 | 주요 영향 업무 | 핵심 판단 |
|---|---|---|---|
| 테이블 → 테이블 ① | 사용자 ID 길이 확대 | 사용자, 그룹, 로그인, 권한, 이력 | 사용자 키를 참조하는 7개 자식 테이블의 수용 길이·외래키 점검 |
| 테이블 → 테이블 ② | 게시글 일련번호 INT → BIGINT | 게시판, 댓글, 첨부 관계 | 복합 외래키를 가진 댓글·첨부 테이블 2개 직접 영향 |
| 테이블 → 소스·화면 ① | 사용자명 USER_NM → ADMIN_USER_NAME | 사용자 조회·설정, 로그인, 내 정보 | SQL 컬럼 참조 수정; Java·화면 이름 유지 가능 여부를 별도 판단 |
| 테이블 → 소스·화면 ② | BTCH_BAS 삭제 | 배치 설정, 이력 조회, 작업 목록, 자동 실행 | 자식 FK와 관리자·배치 모듈 호출 때문에 단독 삭제 부적절 |
| 소스 → 소스 ① | 사용자 권한 저장 메서드 제거 | 사용자별 권한 설정·조회, 로그인 권한 | 호출 컨트롤러·화면 및 권한 데이터 처리 정책 함께 수정 |
| 소스 → 소스 ② | 배치 작업 목록 메서드 제거/시그니처 변경 | 배치 작업 목록 API, 자동 실행 | 시스템 API·스케줄러 2개 직접 호출처 확인 |

DDL에서는 테이블 29개와 외래키 19개를 확인했다. 코드 분석에서는 관리자 업무 JSP 46개, MySQL·Oracle·모듈 중복을 포함한 SQL statement 397개를 조사했다. 컨트롤러 매핑 93개 중 47개에서 서비스·DAO·SQL을 거쳐 제공 DDL 테이블까지 이어지는 정적 경로를 추출했다. 이 수치는 전체 런타임 호출의 완전성이나 실제 실행 여부를 보장하지 않는다.

### 결과 해석 기준

- **DDL 직접 영향**: 명시된 PK/FK 컬럼 관계에 근거한다.
- **코드 직접 사용**: SQL의 컬럼·테이블 참조 또는 Java/JSP의 명시적 호출에 근거한다.
- **간접 업무 영향**: 직접 확인된 처리 결과를 사용하는 업무에 대한 영향 후보다. 분기 조건과 운영 설정에 따라 달라진다.
- **수정 필요**와 **점검 필요**를 구분한다. 컬럼 길이 확대가 모든 Java 소스 변경을 의미하지 않는다.
- DDL만으로 소스·화면 사용처를 알 수는 없다. 아래 소스·화면 결과에는 별도로 제공한 Java·JSP·SQL 분석을 함께 사용했다.

## 2. 테이블 간 영향도

### T1. 사용자 ID 길이를 18자에서 30자로 확대

**변경 대상**: `ADM_USER_BAS.USER_ID` — 현재 DDL에서 `VARCHAR(18)`.

**관련 업무**: 관리자 사용자 식별, 그룹 연결, 로그인 이력, 권한, 즐겨찾기 및 사용자 관련 이력.

#### 1턴: 직접 영향 테이블 확인

**질문**: “ADM_USER_BAS의 USER_ID를 VARCHAR(18)에서 VARCHAR(30)으로 늘리려고 합니다. DDL만 보고 직접 영향받는 테이블을 알려주세요.”

**예상 답변**: 해당 컬럼을 참조하는 자식 테이블 7개가 확인된다.

| 자식 테이블 | 참조 컬럼 | 관련 업무 | DDL FK 시작 줄 |
|---|---|---|---:|
| ADM_USER_FVRT_DTL | USER_ID | 사용자 즐겨찾기 | 653 |
| ADM_USER_PWD_CHNG_TXN | USER_ID | 비밀번호 변경 이력 | 673 |
| ADM_GROUP_USER_REL | USER_ID | 사용자·그룹 연결 | 713 |
| ADM_TRAN_TXN | USER_ID | 사용자 거래 내역 | 723 |
| ADM_LGIN_TXN | USER_ID | 로그인 이력 | 743 |
| ADM_USER_STUS_CHNG_TXN | USER_ID | 사용자 상태 변경 이력 | 753 |
| ADM_USER_ATH | USER_ID | 사용자별 권한 | 773 |

위 표는 DDL상 직접 참조다. 다른 테이블의 `FRST_REGI_USER_ID`, `LAST_CHNG_USER_ID` 같은 감사 컬럼이나 FK 없는 이력 테이블은 이 목록에 자동 포함되지 않는다. 명명 유사성만으로 같은 관계라고 확정하지 않는다.

#### 2턴: 변경 항목과 범위 확인

**질문**: “부모 테이블만 바꿔도 되나요? 각 자식 테이블에서는 무엇을 확인해야 하나요?”

**예상 답변**: 신규 30자 ID가 자식 테이블에도 저장될 수 있어야 하므로 자식 컬럼 길이, FK, 인덱스, 관련 검증을 함께 점검한다. 테이블별 길이 확대 필요 여부를 확인하고 사용하는 DB 버전에 맞춰 적용 순서를 설계해야 한다. 문자열 FK는 DB별 길이 호환 규칙이 있으므로 ‘모든 길이가 반드시 같아야 한다’거나 ‘항상 FK를 삭제하고 재생성해야 한다’고 일괄 단정하지 않는다.

사용자 ID를 저장하지만 FK가 없는 이력·감사 컬럼도 별도 검색해 점검해야 한다. 7개는 DDL에서 바로 확인한 직접 영향 목록이지 전체 업무 영향의 상한이 아니다.

#### 3턴: 업무·소스까지 확장

**질문**: “관련 소스와 화면도 함께 알려주고, 어디를 수정해야 하는지 구분해 주세요.”

**예상 답변**:

| 업무 | 주요 소스 | 화면 | 조치 |
|---|---|---|---|
| 로그인·인증 | ACMSOService.java, AdminLoginDAO.java, AdminLogin_SQL.xml | ACMSO10000.jsp 등 | ID 입력·검증·세션 전달의 길이 제한 점검 |
| 사용자 조회·설정 | ASYAUService.java, AdmUserBasDAO.java, AdmUserBas_SQL.xml | ASYAU40000.jsp, ASYAU40100.jsp | ID 조회·저장·그룹 관계 처리 점검 |
| 사용자별 권한 | ASYAUService.java, AdmUserAthDAO.java, AdmUserAth_SQL.xml | ASYAU40200.jsp, ASYAU50000.jsp | ID 기준 권한 조회·저장 점검 |
| 내 정보·즐겨찾기 | ACMMNService.java 및 연결 DAO·SQL | ACMMN10100.jsp, ACMMN10200.jsp, ACMMN10300.jsp | 사용자 식별자 전달·저장 길이 점검 |

`obix-common/src/main/java/kr/fasol/obix/common/dto/entity/AdmUserBasDTO.java:28`의 `userId`는 String이다. 따라서 길이 확대만으로 Java 타입 변경이 필수는 아니다. 확인한 `ASYAU40100.jsp:205`의 사용자 ID 입력은 읽기 전용이고 명시적 maxlength가 없어, 이 화면에 18자 제한이 있다고 보고하면 안 된다. 다른 입력 경로·검증은 추가 점검 대상이다.

### T2. 게시글 일련번호를 INT에서 BIGINT로 변경

**변경 대상**: `ADM_BULBD_TXN.BLPS_SEQNO` — DDL에서 `INT(11)`. 게시글은 `BULBD_ID`, `BLPS_SEQNO`의 복합 식별 관계를 사용한다.

#### 1턴: 연결 테이블 확인

**질문**: “ADM_BULBD_TXN.BLPS_SEQNO를 BIGINT로 바꾸면 DDL에서 어느 테이블이 직접 영향을 받나요?”

**예상 답변**:

| 자식 테이블 | 복합 외래키 | 영향 | DDL FK 시작 줄 |
|---|---|---|---:|
| ADM_BLPS_BLRP_TXN | BULBD_ID, BLPS_SEQNO | 댓글이 어느 게시글에 속하는지 식별 | 619 |
| ADM_BLPS_APNDX_TXN | BULBD_ID, BLPS_SEQNO | 첨부가 어느 게시글에 속하는지 식별 | 641 |

두 자식 테이블의 `BLPS_SEQNO`도 현재 `INT(11)`로 정의돼 있다. 숫자 타입·부호 등 FK 호환 조건을 점검해야 한다. `INT(11)`의 11을 ‘11자리 정수까지 저장 가능’으로 해석하지 않는다.

#### 2턴: 변경 대상과 순서 확인

**질문**: “게시판 기본 테이블이나 파일 업로드 테이블도 반드시 변경해야 하나요?”

**예상 답변**: 이번 변경이 `BLPS_SEQNO`에 한정되면, `BULBD_ID`로 연결되는 `ADM_BULBD_BAS`는 해당 숫자 컬럼 변경의 직접 대상이 아니다. 파일 업로드 계열도 이름·업무 연관성만으로 직접 ALTER 대상으로 추가하지 않는다. 직접 FK가 확인된 댓글·첨부 테이블의 키와 제약조건을 우선 점검한다. 이후 사용하는 DB 기준으로 FK 처리 → 관련 숫자 컬럼 및 인덱스 변경 → 제약조건 복구·무결성 검증 순서를 검토한다.

#### 3턴: 관련 코드와 화면 확인

**질문**: “해당 키를 사용하는 코드와 확인 가능한 화면은 무엇인가요?”

**예상 답변**: `AdmBulbdTxnDAO`·`AdmBlpsBlrpTxnDAO`·`AdmBlpsApndxTxnDAO`와 각 SQL 매핑, 대응 DTO를 점검한다. 세 DTO의 `blpsSeqno`는 이미 BigDecimal로 선언돼 있다(`AdmBulbdTxnDTO.java:29`, `AdmBlpsBlrpTxnDTO.java:29`, `AdmBlpsApndxTxnDTO.java:29`). 따라서 ‘Integer를 Long으로 바꿔야 한다’고 보고하면 부정확하다. SQL 바인딩·직렬화·비교 로직의 호환성을 확인한다.

확인된 게시판 관리 화면 `ASYOP20000.jsp`의 목록 SQL도 `ADM_BULBD_TXN`을 참조하므로 회귀 점검 대상이다. 다만 완전한 게시글·댓글 CRUD 화면의 활성 호출 경로는 현재 자료에서 확정하지 못했으므로 화면명을 만들어 제시하지 않는다.

## 3. 테이블과 소스·화면 간 영향도

### S1. 사용자명 컬럼 USER_NM을 ADMIN_USER_NAME으로 변경

**변경 대상**: `ADM_USER_BAS.USER_NM` 이름 변경. 타입·사용자 ID 자체는 바꾸지 않는 것으로 가정한다.

#### 1턴: 직접 사용 소스 확인

**질문**: “ADM_USER_BAS.USER_NM 이름을 ADMIN_USER_NAME으로 바꾸면 어느 소스를 고쳐야 하나요?”

**예상 답변**: 우선 해당 컬럼을 직접 참조하는 MyBatis SQL을 수정해야 한다. 예를 들어 MySQL 매핑의 다음 참조가 확인된다.

- `obix-admin/src/main/resources/META-INF/sqlmap/mysql/admin/sy/AdmUserBas_SQL.xml:17,79` — 사용자명 조회.
- `obix-admin/src/main/resources/META-INF/sqlmap/mysql/admin/login/AdminLogin_SQL.xml:28` — 로그인 사용자 정보의 사용자명 조회.
- 위 파일의 다른 SELECT·INSERT·UPDATE·검색 조건 및 실제 운영 방언의 대응 매핑도 함께 검색한다. 특정 SELECT 두 곳만 바꾸고 완료로 판단하지 않는다.

공통 DTO의 `userNm`와 화면 필드는 DB 컬럼 이름과 별개다. 조회 시 `ADMIN_USER_NAME AS USER_NM` 등 기존 매핑을 유지하는 방법을 검토할 수 있으므로 Java·화면 필드까지 무조건 이름을 바꿀 필요는 없다. 쓰기 SQL의 실제 대상 컬럼은 새 이름으로 수정해야 한다.

#### 2턴: 업무와 화면까지 추적

**질문**: “어떤 업무의 어떤 화면에서 사용하는지 항목별로 알려주세요.”

**예상 답변**:

| 업무 | 화면·API 예시 | 연결 소스 | 영향 |
|---|---|---|---|
| 로그인 | ACMSO10000.jsp → /admin/cm/so/ACMSO10001.json | ACMSOController → ACMSOService → AdminLoginDAO | 로그인 사용자 정보 조회와 세션 사용자명 구성 점검 |
| 사용자 목록 | ASYAU40000.jsp → /admin/sy/au/ASYAU40001.json | ASYAUController → ASYAUService → AdmUserBasDAO | 사용자명 목록 표시·검색 점검 |
| 사용자 설정 | ASYAU40100.jsp → ASYAU40101/40102.json | ASYAUService 및 사용자 DAO | 상세 사용자명 조회·저장 점검 |
| 내 정보 | ACMMN10100.jsp → /admin/cm/mn/ACMMN10101.json | ACMMNController → ACMMNService → 사용자 DAO | 개인 정보 표시 점검 |

`ACMSOService.java:264-276`에서는 조회한 사용자명을 DTO로 전달한다. `ASYAU40100.jsp:138,209`에는 사용자명 출력·입력 필드가 있다. 이들은 매핑이 깨질 경우 영향받는 후속 사용처이며, 별칭으로 기존 계약을 유지하면 해당 Java·화면 코드를 유지할 수 있다.

#### 3턴: 수정 우선순위와 검증

**질문**: “반드시 수정할 부분과 유지 가능한 부분을 나누고 테스트 항목을 알려주세요.”

**예상 답변**:

1. **필수 수정**: DB 컬럼을 직접 지정하는 읽기·쓰기 SQL, 해당하는 DDL·마이그레이션 정의.
2. **설계 선택**: SQL 별칭 또는 resultMap을 유지해 `userNm`를 계속 사용할지, DTO·API·화면까지 새 이름으로 변경할지 결정.
3. **회귀 검증**: 로그인 성공 및 사용자명 표시, 사용자 목록·검색, 상세 조회, 사용자명 변경 저장, 내 정보 조회.
4. **범위 구분**: 이름을 바꾸는 컬럼은 USER_NM이다. USER_ID 외래키 7개를 이 변경의 직접 ALTER 대상으로 혼동하지 않는다.

### S2. 배치 기본 테이블 BTCH_BAS 삭제

#### 1턴: 직접 테이블 영향 확인

**질문**: “BTCH_BAS를 삭제하려고 합니다. 관련 테이블과 SQL을 알려주세요.”

**예상 답변**: `BTCH_EXE_TXN.BTCH_JOB_ID`가 `BTCH_BAS.BTCH_JOB_ID`를 참조한다(DDL:783). 두 컬럼은 VARCHAR(10)이다. FK가 유지되는 상태에서는 부모 테이블을 단독 삭제하는 계획이 적절하지 않다. 기존 실행 이력을 보존할 것인지, 참조 관계를 대체할 것인지 먼저 결정해야 한다.

테이블 참조는 다음 SQL 파일에서 확인된다. 각 MySQL·Oracle 파일을 구분해 실제 사용하는 방언을 점검한다.

- obix-admin/.../sqlmap/mysql/admin/sy/BtchBas_SQL.xml
- obix-admin/.../sqlmap/mysql/admin/sy/BtchExeTxn_SQL.xml
- obix-batch/.../sqlmap/mysql/comm/BtchExeTxn_SQL.xml
- 위 세 파일의 Oracle 대응 매핑.

#### 2턴: 영향받는 업무·소스·화면 확인

**질문**: “관리 화면 외에 실제 배치 실행도 영향을 받나요?”

**예상 답변**:

## 4. 소스 내부·소스 간 영향도

### C1. 사용자 권한 저장 ASYAUService.ASYAU40202 제거

#### 1턴: 직접 호출처 확인

**질문**: “ASYAUService.ASYAU40202를 없애면 어디를 수정해야 하나요?”

**예상 답변**: 해당 메서드의 직접 호출은 `ASYAUController.java:527`에서 확인된다. 해당 컨트롤러 메서드의 API는 `/admin/sy/au/ASYAU40202.json`이며, `ASYAU40200.jsp:180`에서 호출한다.

연결: `ASYAU40200.jsp` → `ASYAUController.ASYAU40202` → `ASYAUService.ASYAU40202` → `AdmUserAthDAO` → `AdmUserAth_SQL.xml` → 사용자 권한 및 이력 테이블.

컨트롤러 호출을 남긴 채 서비스 메서드를 삭제하면 컴파일 오류가 발생한다. API를 제거하고 화면 호출을 남기면 사용자 권한 저장이 동작하지 않는다.

#### 2턴: 메서드 내부 처리와 데이터 영향 확인

**질문**: “이 메서드가 내부에서 하는 일과 관련 테이블은 무엇인가요?”

**예상 답변**: `ASYAUService.java:696-722`에서 다음 순서를 확인했다.

1. 현재 관리자 ID를 최초등록자·최종수정자로 설정.
2. `insertAdmUserAthHst` 호출(704행): 기존 사용자 권한 이력 저장.
3. `resetAdmUserAth` 호출(706행): 기존 권한 초기화.
4. `screnList`가 있으면 `mergeBulkAdmUserAth` 호출(717행): 화면별 권한 일괄 저장.

주요 테이블은 `ADM_USER_ATH`, `ADM_USER_ATH_HST`다. 이력 저장·초기화·저장 중 일부만 없애는 변경은 권한 손실이나 감사 이력 누락 가능성이 있으므로 하나의 처리 흐름으로 검토한다. 트랜잭션의 실제 경계는 별도 설정을 확인해야 하며 이 메서드만 보고 원자성을 확정하지 않는다.

#### 3턴: 안전한 제거 범위 결정

**질문**: “그럼 DAO와 권한 테이블도 같이 지워도 되나요?”

**예상 답변**: 안 된다. 권한 저장 기능 제거와 권한 조회·적용 기능 제거는 다르다. `ASYAU40201.json`, `ASYAU50001.json`과 로그인 권한 로딩에서도 사용자 권한을 사용한다. `AdmUserAthDAO` 전체나 권한 테이블을 함께 지우는 것은 별도 영향 분석이 필요하다.

- 화면의 저장 기능·호출 처리, 컨트롤러 API, 서비스 메서드를 함께 정리하거나 대체한다.
- 기존 권한은 계속 적용할지, 다른 관리 방식으로 이전할지 결정한다.
- 권한 조회와 로그인·메뉴 접근, 그룹 권한 병합 동작을 회귀 검증한다.
- ‘직접 호출 한 곳’은 외부 API 소비자·리플렉션·운영 사용까지 없다는 의미가 아니다.

## 5. 공통 결론과 제약

1. 테이블 간 직접 영향은 DDL의 PK/FK로 도출할 수 있다. 소스와 업무·화면 영향까지 제시하려면 Java·SQL·화면 파일이 추가로 필요하다.
2. 테이블에 FK가 없어도 SQL 조인·프로그램 저장·이력 적재 등으로 업무상 연관될 수 있다.
3. 특정 서비스 메서드 제거와 해당 DAO·테이블 전체 제거는 별개의 변경이다. 공유 사용처를 반드시 분리한다.
4. MySQL·Oracle 매핑이 함께 제공되므로 운영 방언 확인이 필요하다. SQL 정의가 있다는 사실과 활성 호출이 확인됐다는 사실을 구분한다.
5. 이번 결과는 정적 분석이다. 외부 JAR, 운영 DB 저장 객체, 동적 SQL/URL, 스프링 AOP·DI, 리플렉션, 오버로드, 미제공 외부 시스템은 추가 확인 대상이다. 삭제 가능 여부나 ALTER 성공을 실행으로 검증한 결과는 아니다.
6. 요청 예시의 ‘계좌조회’는 이 샘플에서 독립된 업무 화면·API 경로를 확인하지 못해 시나리오로 채택하지 않았다. 계좌번호 포맷 유틸리티만으로 존재하지 않는 업무를 만들어 설명하지 않았다.
